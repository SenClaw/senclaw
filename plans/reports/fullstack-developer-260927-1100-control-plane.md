## Follow-up: agent_status and L1 offload wired live

Lead's decision (relayed mid-task): §17 P0 names the status bar and the two-zone assembler, so leaving them unwired left P0 incomplete — wire both now, with a design that cannot corrupt history. Implementation, exactly per the lead's spec:

**`<agent_status>` per LLM call** (`src/zen_core/conversation.rs`):
- Added `QueryConfig.agent_status: bool` (two construction sites: `zen_core::engine.rs` reads the live setting via `load_control_plane_settings(&control_plane::default_config_path())` per turn, same pattern as `route_skill`; `tools/task.rs` sets `false` for subagents — best-effort helpers, no status line for them).
- New `conversation::outgoing_messages(messages: &[Message], agent_status_on: bool, input: &AgentStatusInput) -> Cow<[Message]>`: off returns `Cow::Borrowed(messages)` (the identical borrow, zero copy); on clones once and pushes one `ContentBlock::Text` onto the *last user-role* message (where tool results already live internally — `ContentBlock::ToolResult` is carried inside a `role: "user"` message, confirmed by reading `create_user_message`'s call sites).
- **Verified in the adapter code before wiring**, per the lead's instruction: `query_llm.rs::anthropic_content_blocks` places every block type from one message into one content array regardless of type, so an extra trailing `Text` block after existing `Text`/`ToolResult` blocks is valid Anthropic shape with no change needed. `query_llm.rs::openai_messages_for_api` accumulates `Text` into a buffer and flushes a `role:"tool"` message per `ToolResult`, then flushes whatever text is left (including a `Text` block that arrived *after* `ToolResult`s) as a **separate trailing `role:"user"` message** — exactly the shape OpenAI needs, again already correct with zero provider-specific code.
- Only the one call site inside the turn loop (`query_llm::query_llm(...)`) was changed; the compaction call in `summarize_history` builds its own message list and was never touched — a doc comment on `summarize_history` now states that explicitly.
- `AgentStatusInput.call_index`/`call_budget`/`elapsed_secs` are real (from the loop's own `turn`/`max_turns` counters and an `Instant` captured once at the top of `query()`); `original_goal` is captured once via a new `goal_text()` helper reusing the existing `last_real_user_index` (so it survives mid-loop compaction unchanged); `todo_open`/`todo_total`/`pending_events` are left at `0` — `StateManager` and the event/dispatch queues are not reachable from this seam without new plumbing, and `render()` already degrades those to "0/0 open" safely. Documented in `docs/control-plane.md` §4.1, not silently simplified.
- 5 new tests in `conversation.rs`, one per the lead's requirement: `agent_status_never_mutates_the_persisted_history` (a), `agent_status_on_appends_exactly_one_trailing_block_to_the_last_user_message` (b), `a_static_prefix_hash_does_not_depend_on_agent_status` (c — structural: `outgoing_messages` never receives `system_prompt`), `agent_status_off_returns_the_same_borrow_untouched` (d — asserts `Cow::Borrowed`, not just equality), plus `goal_text_captures_the_original_real_user_message_not_a_tool_result_carrier`. Requirement (e) is the full `cargo test --workspace` run below.

**L1 offload** (`src/zen_core/run_tools.rs`):
- Wired at the exact point `result_for_assistant` (the string a tool's success result becomes) is packed into `ContentBlock::ToolResult` — after LSP diagnostics are appended, so the check sees the final text.
- Cheap in-memory length check (`workspace::OFFLOAD_THRESHOLD_BYTES` = 8000) runs *before* reading `config.json`, so a normal-sized tool result never touches disk for a settings check. Only when both the length and `controlPlane.workspace.substituteToolOutput` are true does `Workspace::write_artifact(tool_id, &result)` run, replacing the text with its head+tail preview.

- **`may_auto_approve`'s floor differs from Bash's static registry entry on purpose** — a command-bearing call defers to the risk list (matching the existing gate's finer, per-call Jev judgment); a tool with no command context (e.g. a hypothetical future high-risk tool with no text to parse) falls back to the static `risk_tier≥3 && !reversible` floor. ## Security fixes: H1 path traversal, L5 safe_id collisions

Per `plans/reports/code-reviewer-260927-1127-daemon-security-correctness.md`. Scope stayed inside `src/control_plane/**`; no change was needed to `src/gateway/ui_server/control_plane.rs` — its handlers just forward the raw path param, and the fix is entirely in the functions they call.

**H1 — `GET /api/traces/:id` arbitrary `.json` read (`src/control_plane/trace.rs::read_by_id`):**
- Before: `id.split_once(':')` then joined both halves straight onto `root()` with zero validation, despite a comment claiming the input was already `safe_id`-shaped — true only for ids `list_all` produces, not for the raw HTTP path param. `GET /api/traces/..:../config` resolved to `~/.senclaw/config.json` (provider API keys), reachable by any loopback peer under the default `auth: auto` mode.
- Fix, two independent layers: (1) both `chat` and `stem` must satisfy a new `control_plane::is_safe_path_component` — `!part.is_empty() && safe_id(part) == part`, i.e. the component must already be in `safe_id`'s mangled form (any traversal-relevant character makes this false in one check: `.`, `/`, `\`, `:` are all outside `safe_id`'s allowed set, so `..`, absolute paths, and nested separators are all rejected together); (2) the resolved path is canonicalized and checked against a canonicalized `root()` via new `control_plane::path_stays_under`, so the fix does not depend solely on the character-set check holding forever.
- New test `read_by_id_rejects_path_traversal_and_cannot_read_outside_the_traces_root`: places a real secret file next to the (redirected) traces root and proves `..:../config`, `a/b:c`, `c:a/b`, `/etc:passwd`, `etc:/passwd`, `..:config`, and a raw percent-escape all resolve to nothing, then proves the secret file *is* readable by ordinary means (so a bug that made every lookup fail could not masquerade as a fix).

**Audited every other control-plane file API for the same class:**
- `SpecRegistry::set_mode` (`PUT /api/control-plane/specs/:id/mode`) writes `dir.join(format!("{id}.json"))` from the raw path param. `self.by_id.get(id)` already constrains `id` to a key that came from a previously-`validate()`d `Spec` (bundled or override) — but that chain had a real hole: a manually-placed override file's `id` comes from its *JSON content*, not its filename, and `Spec::validate()` never checked it was filename-safe. Fixed at the root: `Spec::validate()` now rejects any `id` that is not dot-separated segments of `[A-Za-z0-9_-]` (dots are the legitimate namespace separator — `"input.guard.override"` — so a plain `is_safe_path_component` would wrongly reject every real spec id; the per-segment rule accepts real ids and still rejects `/`, `\`, and `..` in one check, since `..` always decomposes into an empty segment). `set_mode` also re-checks `is_valid_spec_id(id)` and that the joined path's parent is exactly the override directory, as defense in depth that does not rely on the registry-load-time check alone.
- Workspace artifacts (`Workspace::write_artifact`), G1 decision-input files (`record_decision_input`), and the L1-offload write path — all already sanitize their id/jid components through `safe_id` before joining (pre-existing, confirmed still correct; `write_artifact_confines_the_call_id_to_one_path_component` already covered this). None of these are exposed for *reading* an arbitrary path via HTTP the way `read_by_id` was — the read side was the actual gap.
- `POST /api/control-plane/decisions/replay` (`ladder::force_ask`) does no filesystem path construction from its input at all (`spec_id` is a map lookup only) — not in this class.
- New tests: `is_valid_spec_id_accepts_real_ids_and_rejects_traversal_shapes`, `validate_rejects_a_spec_id_shaped_like_a_traversal`, `a_malicious_override_file_is_rejected_not_loaded_into_the_registry` (places a file with a crafted `{"id": "../../etc/evil", ...}` and confirms `SpecRegistry::load()` reports it in `errors` and never inserts it into the registry).

**L5 — `safe_id` collided distinct jids (`src/control_plane/mod.rs`):**
- Before: every non-`[A-Za-z0-9_-]` character folded to `_`, so `"a:b"` and `"a_b"` both produced `"a_b"` — two different chats' traces/workspaces could intermix.
- Fix: `safe_id` now returns the mangled string unchanged when mangling did not change anything (existing on-disk names for already-safe jids keep resolving), and appends an 8-hex-char SHA-256-prefix hash of the *original* input whenever mangling did change something, making the mapping injective for the colliding case while staying a fixed point of itself (`safe_id(safe_id(x)) == safe_id(x)` always — required for `is_safe_path_component` to accept every id `list_all` hands out, verified by a dedicated test).
- New tests: `safe_id_is_injective_for_inputs_that_used_to_collide` (the literal `"a:b"` vs `"a_b"` case from the report), `safe_id_output_is_a_fixed_point_of_itself`, plus `is_safe_path_component_rejects_traversal_shapes` and `path_stays_under_rejects_escape_and_accepts_a_real_child` for the two new shared helpers.
- Checked for breakage: every existing test jid (`"trace-test-1"`, `"jid-artifact"`, etc.) is already alphanumeric/dash, so `safe_id` mangles nothing for any of them and their on-disk paths are byte-identical to before — confirmed by the full test suite staying green with no hardcoded-path test needing an update (the one test that does assert a literal artifact path, `l1_offload_only_replaces_a_large_result_when_the_switch_is_on` in `run_tools.rs`, computes the expected path by calling `safe_id` itself rather than hardcoding a string, so it tracked the change automatically).
